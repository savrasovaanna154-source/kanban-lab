# План тестирования

## 1. Введение

**Объект тестирования:** веб-приложение «Kanban-доска» (клиент + сервер + БД).
**Цель тестирования:** убедиться в соответствии функциональным (FR-01…FR-29) и нефункциональным (NFR-01…NFR-12) требованиям.

**В области тестирования:**
- Аутентификация и авторизация.
- CRUD проектов, досок, колонок, карточек.
- Drag-and-drop карточек.
- WIP-лимиты.
- Поиск и фильтрация.
- API-контракты.
- Производительность, безопасность, юзабилити.

**Вне области тестирования:**
- Мобильные приложения (iOS/Android).
- Интеграции с внешними сервисами.

## 2. Ресурсы

| Роль | Ответственность |
|---|---|
| Разработчик | Модульные, интеграционные тесты |
| Тестировщик | API, E2E, нагрузка, безопасность |
| CI/CD | Регрессионный прогон на каждый push |

**Окружения:**
- Local (Codespaces) — разработка.
- Staging — предпродакшн.
- Prod — эксплуатация.

**Инструменты:** Jest, Supertest, Testcontainers, Playwright, k6, OWASP ZAP, GitHub Actions, Newman.

## 3. Расписание

| Этап | Длительность |
|---|---|
| Анализ требований и составление плана | 1 день |
| Разработка + модульные тесты | 5 дней |
| Интеграционные + API-тесты | 2 дня |
| E2E-тесты | 2 дня |
| Нагрузочные + security-тесты | 1 день |
| Подготовка отчёта и защита | 1 день |

## 4. Критерии начала и окончания

**Критерии начала:**
- Требования зафиксированы в `REQUIREMENTS.md`.
- Окружение (Docker + PostgreSQL) поднято.
- Миграции БД выполнены.

**Критерии окончания:**
- Покрытие строк ≥ 80%, ветвей ≥ 70%.
- Нет открытых багов уровня Blocker / Critical.
- Открытых Major ≤ 3 с известным workaround.
- Все E2E-сценарии проходят в Chrome, Firefox, Edge.
- ZAP не находит уязвимостей уровня High.
- Нагрузочный тест выдерживает 1000 RPS при p95 < 200 мс.

## 5. Риски и меры их снижения

| Риск | Митигация |
|---|---|
| Нехватка времени | Приоритизация: сначала FR-01…FR-15 |
| Нестабильные E2E-тесты | retry, явные ожидания, стабильные селекторы (`data-testid`) |
| Ограничения Codespaces (нет Docker) | SQLite как fallback для БД |
| Отсутствие реального staging | Локальный docker-compose |
| Ошибки в тестовых данных | Фабрики фикстур, изоляция БД на каждый тест |

## 6. Артефакты

- `docs/TEST_CASES.md` — тест-кейсы.
- `docs/BUG_REPORTS.md` — баг-репорты.
- `docs/TEST_REPORT.md` — итоговый отчёт.
- `coverage/` — HTML-отчёт покрытия (Jest).
- `playwright-report/` — отчёт E2E.
- `k6-summary.json` — отчёт нагрузочного теста.

## 7. Виды тестирования

| Вид | Инструменты | Ответственный |
|---|---|---|
| Модульное | Jest, ts-jest | Разработчик |
| Интеграционное | Supertest, Testcontainers | Разработчик / тестировщик |
| API | Postman, Newman | Тестировщик |
| E2E | Playwright | Тестировщик |
| Нагрузочное | k6 | Тестировщик |
| Безопасность | OWASP ZAP, npm audit, Snyk | Тестировщик |
| Юзабилити | Ручное, чек-листы | Тестировщик |
| Регрессионное | Автотесты в CI | CI/CD |

## 8. Управление дефектами

**Severity:** Blocker / Critical / Major / Minor / Trivial.
**Priority:** High / Medium / Low.

Жизненный цикл: `Open → In Progress → Fixed → Verified → Closed`.

Правило: **Blocker и Critical закрываются до релиза; Major — до релиза, если есть время; Minor и Trivial могут быть отложены с обоснованием.**
